# Decisions log

Decisions for the India Petroleum API (PPAC data). Newest at the bottom. Written before the code that follows them.

## 2026-10-22 — Source, shape and ingestion (from the PLAN)

- **Source:** PPAC's daily metro PDF ("RSP of Petrol and Diesel in Metro Cities since 16.6.2017"), reuse allowed free with accurate reproduction and acknowledgement (https://ppac.gov.in/terms-conditions). OMC sites are not a source (they bar database building).
- **Serving:** the public API reads stored JSON only. It never calls PPAC at request time; a separate Actions job downloads, parses, checks and commits the data.
- **Scope v1, module A:** four metros (Delhi, Mumbai, Chennai, Kolkata), petrol and diesel, daily since 2017-06-16. Module B (monthly statistics from data.gov.in) follows and needs the owner's key and licence reading.
- **Project name:** `india-petroleum-api` (renamed from `ppac-petroleum-api` on 22/10/2026 at the owner's request).

## 2026-10-24 — Build decisions

- **Order:** the owner asked to build now instead of waiting for the Phase 1 proof week. Offline phases run ahead; deploy, the production cron and retiring `fetch-proof.yml` still wait for the Phase 1 verdict (Plan issue 4).
- **Text extraction:** `pdftotext -raw` read as tokens. `-layout` is wrong for this file (Plan issue 5). Same 3,417 days from Xpdf 4.00 and poppler 26.01.0.
- **Stored format:** `data/fuel/daily.json` one day per line, oldest first; `changes.json` one price move per line; `meta.json` with source URL, posted date, sha256, fetch time, range. A daily append is a one-line diff.
- **Provenance is never guessed:** the builder takes the PDF, its URL and its fetch time as inputs and hashes the PDF itself.
- **Date meaning:** `date` is PPAC's "Date of Revision" as published. PPAC's footnote says a daily change applies from 6:00 AM; the API does not claim a pump date.
- **Module type:** the whole repo is ES modules (`"type": "module"`), backend included. Express 5, `cors`, `express-rate-limit` 8.
- **Library facts used (context-brief, 2026-10-24):** `express@5.3.0` is npm latest; `express-rate-limit@8.7.1` is latest, uses `limit` (not `max`), `ipv6Subnet` 56 and `standardHeaders: 'draft-8'` (Context7 `/express-rate-limit/express-rate-limit`); `app.set('trust proxy', 1)` is spoof-safe on Vercel (cached brief `vercel-express-function-region-cache`, verified 2026-10-15); Express 5 needs a 4-argument error handler after the 404 handler to keep errors as JSON (cached brief `express-5-error-handling`, 30-day TTL expired 2026-09-15, so the project's own tests re-check 404 and 500 and a malformed query as JSON).
- **Rate-limit headers off:** the CDN caches `/v1` responses (`s-maxage`), and a cached `RateLimit-Remaining` is served stale to every caller; the limiter stays at 100 requests per 15 minutes per IP with `RATE_LIMITED` in the envelope.

## 2026-10-24 — Portal (Task 4.3)

- **Scaffold used for the skeleton only.** `scaffold-frontend.js` ran with the project's real domain passed through its `decideFn` hook (the script hardcodes `finance-tax`). The design chain answered `terminal-dev` / `paper-cobalt` / `inter-jetbrains` with confidences 0.25, 0.73, 0.44, 0.64 (all under the 0.8 auto gate: the model was not sure), and `paper-cobalt` is the GST portal's palette. Its pages are GST-shaped (an HSN playground, a chapters explorer, a ⚡ logo, hardcoded counts), so only the routing, prerender, sitemap and `vercel.json` ideas are kept; every page is rewritten for fuel prices. The route list, 404 page, `SITE_URL` handling and JSON-LD follow the newer EV portal (the scaffold predates `CONVENTIONS.md` on the 404 page and `"framework": "vite"`).
- **Identity: a price circular, derived from the domain.** PPAC publishes a government table of rupee figures; the competitors found in the research (GoodReturns, MyPetrolPrice) are ad-heavy news pages. So: warm paper canvas, ink-green text, a serif for headings (Source Serif 4), IBM Plex Sans for text and IBM Plex Mono for every figure so decimals line up. Two series colours are fixed meanings across the whole site: petrol is deep green `#0B6B50`, diesel is burnt orange `#A23B0C` (distinguishable with red-green colour blindness because of lightness and hue, and always labelled in text). Light theme only (`color-scheme: light`). It shares nothing with the GST (cobalt paper), EV (amber on graphite) or MSP (forest and ochre) portals.
- **Layout rules:** left-aligned, no centred hero stack, no eyebrow labels (banned by the owner), no emoji icons, no card grid, one primary action per screen. The hero leads with the real artifact, today's price board and the 2017-2026 chart, both drawn from `data/fuel/` at build time. No entrance animation; colour transitions of 120 ms at most, off under `prefers-reduced-motion`.
- **Written from memory, not retrieved:** the price board, the SVG chart, the form and the tables. No registry (shadcn, React Bits, Magic UI, Aceternity) ships a price table or a time-series chart that fits a prerendered, dependency-free page, and none of the registries' effects serve this content. Stated here so nobody reads these components as registry code.
- **No chart library.** Eight series of at most 3,417 points are drawn as an SVG path from min/max-decimated data, which prerenders on the server and adds no dependency. A library (uPlot, Recharts) would add 40-90 kB and canvas or client-only rendering for a chart with no zoom requirement.
- **No Tailwind.** Plain CSS with custom properties in `index.css`, as the scaffold does. One stylesheet is easier to audit for contrast and spacing than utility classes across seven pages.
- **Build-time data, run-time API.** `frontend/scripts/build-snapshot.mjs` reads `data/fuel/*.json` into `src/generated/snapshot.json` before every build (the latest day, the Delhi history, the largest moves, counts). Prerendered pages therefore carry real numbers; the playground and status page call the live `/v1` API. The daily data commit redeploys the site, so the snapshot is never older than the data.
- **`SITE_URL`:** the canonical origin comes from `SITE_URL`, else Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, else the build emits no canonical tags, sitemap or robots file (same rule as EV: never point crawlers at a host that is not serving the site). The GSC token file is an owner input and is not invented.
- **Guides:** three, with numbers computed from the stored data and pinned to windows that end on a fixed past date, so a daily append cannot make them false. A test recomputes each number from `data/fuel/`.

## 2026-10-24 — Production-readiness audit (quality gate, attempt 1)

`prod-bug-auditor` returned 1 high, 2 medium, 3 low findings. Each was re-checked against the code before acting; what was decided:

- **Fixed: `fuel-ingest.yml` ran `npm test` without `npm ci`.** Since the backend tests joined `npm test` they import express, which a clean runner does not have, so the first real run after a new PPAC day would write data, fail the Tests step and never commit. The only successful run predates the backend tests. The workflow now installs first, and a test refuses any workflow that runs `npm test` without an earlier `npm ci`.
- **Fixed: no plausibility check on published prices.** A typo in PPAC's table (say 1021.20 for 102.12) passed every check, was served as official, and would later block ingestion as a restatement. The builder now refuses (`IMPLAUSIBLE`, exit 3) a price outside 20 to 500 rupees or a day-over-day move above 20 rupees (the largest real move since 2017 is 12.48, corrected below). A real shock is approved by listing the dates in `ingest/approved-moves.json`, the same pattern as `approved-restatements.json`.
- **Fixed: a failed listing-page fetch aborted the run** instead of trying PPAC's second page. Page discovery is now one function that moves to the next page on a network error and still stops at once on a TLS error (never worked around).
- **Fixed: the playground could show an error beside good results** when a superseded request was aborted while its body was still arriving. `apiGet` now rethrows the abort.
- **Fixed: `npm run dev` rendered a blank page** because `index.html` carries the unreplaced `__SITE_URL__` canonical. The canonical update ignores an unparseable URL.
- **Reworded: the rate limit.** The limiter keeps its counters in each serverless instance, so "100 requests per 15 minutes per IP" is not a global guarantee on Vercel. The docs, README and the 429 row now say it is counted per server instance. A global limit would need Vercel's firewall rules, an owner setting.
- **Fixed: stale comment** in `fuel-ingest.yml` pointing at a `docs/PROOF-1.md` that does not exist; it points at `docs/GO-LIVE.md`.
### Attempt 2 (second audit pass, after the fixes above)

All six first-pass items were found in the code; the pass also found defects the fixes introduced. Each was re-checked before acting:

- **Real defect, fixed: the "stored history is plausible" test had no approved dates.** A real shock approved in `approved-moves.json` would be written by the ingest step and then fail `npm test` in the same job, so it could never be committed. The test now passes the approved dates through, and a second test checks the file holds only real dates.
- **Fixed: a failed primary page was invisible** when the fallback page answered, and an unreachable page could be reported as `NO_LINK` ("PPAC removed the link"). `discoverLatest` now returns the swallowed page errors, the run logs them in `page_errors` (shown by `summarize-proof.js`, so the proof week can see a flaky primary page), and it throws the first network error when no page gave a link and any page was unreachable.
- **Fixed: the API still said "100 requests per 15 minutes per IP" without the per-instance caveat** in `/health` and in the 429 body, and the docs printed that sample under the new caveat. Both strings now carry it; a test ties the two together.
- **Fixed: the refusal message hid the second date of a spike** after five detail lines. It now lists every affected date, inline after `dates:`.
- **Corrected: the largest real move is 12.48** (Mumbai diesel, 2021-11-04), not the 11.75 written above, which was Delhi diesel. The 20 rupee limit still clears it with a margin of 7.5.
- **Added: `workflows.test.js` now checks each job, including `run: |` blocks,** not the file as a whole. A CI workflow (`ci.yml`) runs the tests and the build on every push and pull request, because pass 1 found nothing gated merges.
- **Pass 3 (scoped to the fixes above) found no functional regression and these residuals; all are fixed in the follow-up commit without a fourth audit, because the gate allows no more re-runs:**
  - the runbook said "two days without new data trip the freshness alarm" for a download error, but the freshness job only runs after a successful ingest, so on a download error or a refusal the red run is the alarm;
  - the page errors were lost when discovery threw (both pages down, or one down and the other without a link): they are now attached to the thrown error and written to `page_errors` by `run()`;
  - `ci.yml` is a signal, not a gate, unless the owner makes `verify` a required check; its comment said otherwise, and `cancel-in-progress` could drop the verdict for a commit pushed to main, so it now cancels only superseded pull-request runs;
  - a stored day that vanished from PPAC's table is always refused and approving its date never clears it, but the message hinted at approval: the hint now fits the case, and the runbook says so;
  - the CONTINUITY runbook offered a per-fuel option that cannot apply (petrol and diesel come from the same row), and the refusal message puts the dates inline after `dates:`, not "on its own line" as written above;
  - `frontend/scripts/snapshot.test.mjs` asserted facts about the newest data (top moves, longest pause), so a future real shock or pause could fail CI after a good ingest; those tests are now pinned to the data up to 2026-10-23.
- **Optional polish, not done:** approving one city's shock still waives the whole day for the other series. Per-series approval would need a second file format; the message lists what is being waived instead.

- **Left as is, on purpose:** `/health` always says operational (staleness is shown by `/v1/meta` and the freshness job); the failed-run proof-log line is not committed (transitional until `fetch-proof.yml` retires); `engines.node ">=22"` stays open (Vercel's project setting decides); the og-image shows the prices of the day it was rendered, and nothing claims it is live.

## 2026-10-24 — Live data, resilient ingestion, compact UI (owner request after go-live)

The owner asked for: no hardcoded May dates; the newest fetched data shown dynamically; a chart of the last two to three months; the daily fetch checked end to end with retries and edge cases; a more compact playground; robust and developer-friendly behaviour. Decisions:

- **The API reads the newest committed data at run time.** Until now the function served the files bundled at deploy time, and Vercel is not linked to GitHub, so a data commit would never reach the site. The function now fetches `meta.json`, `daily.json` and `changes.json` from this repository's public raw URL (`DATA_BASE_URL`, default the `main` branch), at most once per `DATA_TTL_SECONDS` (default 600) per instance, with conditional requests (ETag). It swaps data in only after validating it (shape, whole-series continuity, plausible prices, newer than or equal to what it holds, the three files agreeing); on any failure it keeps serving the last good data and says so in `/v1/meta` (`data_source`, `checked_at`, `refresh_error`). The bundled copy is the fallback, so a GitHub outage cannot take the API down. This is still "stored JSON only": it never contacts PPAC; the repository is the store. `DATA_REMOTE=off` disables it (tests, local runs).
- **The frontend keeps the prerendered snapshot only as first paint and for crawlers.** On load it asks the API for `/v1/meta`, `/v1/prices/latest` and the chart range, shows those, and falls back to the snapshot with a visible "showing data from <date>" notice if the API is unreachable. A banner appears on every page when the newest price is more than two days old. No date literal drives what the pages display; the three guides stay dated articles with pinned, tested figures.
- **The home board shows how long a price has held**, from a new additive field `meta.last_change` on `/v1/prices/latest` (per fuel and city: date, from, to), instead of scanning the change history in the browser.
- **Chart:** last three months by default, with one-year and all-time buttons and a city selector; all of it from the API, not from build-time data. A flat three months is a true picture and is described in words.
- **Docs and playground examples are relative to the newest date** (last 7 days, last 365 days of changes, last 30 days), computed when the site is built and by the API's own answers, not fixed windows.
- **Schedule:** `fuel-ingest.yml` runs every three hours (minute 20) and is idempotent. PPAC's posting time is irregular (the 23 Oct table was up by 06:22 UTC on 23 Oct; at 12:50 UTC on 24 Oct the 24 Oct table was not), so a fixed hour would either miss it or wait a day, and a run costs about four seconds and two to three requests. The owner's request of 24/10 supersedes the one-week proof rule, so the cron is on; `fetch-proof.yml` loses its schedule (manual dispatch stays) so two jobs do not hit PPAC.
- **Retries:** listing pages 3 attempts (waits 5 s and 20 s) with fallback to the second page; the PDF download 4 attempts (30 s, 120 s, 300 s) as before; the three-hourly schedule is the outer retry. A failed run opens or updates one GitHub issue ("ingest failed") and closes it on the next success. The commit step retries `pull --rebase` and `push` three times.
- **A stale source is not an error.** If PPAC serves a file older than what is stored and every day in it matches the stored day, the run is a no-op with a notice. Missing days in the middle, or changed prices, are still refused.
- **Cache:** `/v1` answers are cacheable at the CDN for 10 minutes (was an hour) so a new day shows within about ten minutes of the API loading it.
- **Playground:** one compact form row, results beside each other on a wide screen (chart and table above the fold, code samples in collapsed sections), shorter chart, defaults from the newest date.

## 2026-10-24 — Frontend live-data layer, compact playground, data-store audit (owner list items 1, 2, 4 and 5)

What the owner asked for is the section above ("Live data, resilient ingestion, compact UI"); this records how the frontend half was built and what the audit changed.

- **Three states, one shape (`lib/live-state.js`).** `snapshot` (build-time figures, also the prerendered HTML), `live` (the API's `/v1/meta` and `/v1/prices/latest`) and `offline` (the API did not answer; the snapshot stays and says so). The prerender renders `AppContent` alone, so static HTML never carries a banner and says "Data up to <date>. Checking for newer figures." The browser entry wraps it in `LiveDataProvider`, which asks the API on load, again every ten minutes while the tab is visible, and when the tab becomes visible again (never more than once a minute). A failed refresh keeps live figures already on screen; only the first load falls back to the build. API answers are shape-checked (dates, numbers, all eight prices, an https `source_url`, a text `sha256`), so a malformed answer becomes the offline state instead of `NaN` or a thrown render.
- **One banner rule.** More than two days behind (the same limit as `ingest/freshness.js` and the status page, now one constant) puts a banner under the header on every page with a link to `/status`. Offline puts one with a retry button, the reason, and how old the build is (counted in India days on the visitor's clock). Two days is normal around a weekend and shows nothing.
- **The home chart reads the API.** `HistoryChart` fetches `/v1/prices` for the city and range (3 months, 1 year, All), always counted back from the newest day the API reports (`lib/range.js`: calendar months with end-of-month clamping, never before the first stored day). A range longer than the API's 3,660-day limit is fetched in contiguous parts and joined, all or nothing (`lib/history.js`); "All" becomes two requests around June 2027. A loaded selection is cached; while a new one loads the old chart stays up under its own labels, dimmed; a failed one keeps the old chart, names it, and offers Try again. The snapshot no longer stores history (17 KB; it held a full Delhi series before); `examples.recent` (the API's own answer for Delhi's last three months) is only the first paint and the fallback. A flat quarter is true, so each chart has a sentence per fuel (`lib/summary.js`: held, rose or fell, revision count, latest revision date). The numbered largest moves are kept and drawn only when Delhi is selected and the date is inside the range; the list stays on the page for crawlers.
- **Examples follow the data.** `scripts/example-paths.mjs` builds every example request from the newest stored day: docs range 7 days, changes 365 days, error example 5 days, playground 30 days, chart 3 months. A test fails if a calendar date from a fixed year appears.
- **`api.json` cannot follow the data.** It is a static file and the hub's manifest has no date templating, so its two probe routes could not be made relative. The prices route is anchored on the first stored day (2017-06-16 to 22, which never goes stale) and the changes route has no window, so the API's own default (a year back from the newest day) applies. `backend/test/manifest.test.js` refuses any later date in a probe route and checks that each answers 200 with rows. The `dataset` block in `api.json` (`days`, `source_posted_date`, `source_pdf_url`) still records the day of the last manual edit and nothing compares it with live data.
- **Playground.** The form follows the newest day until the visitor edits a field: it loads the live 30-day answer on arrival and again if the API reports a newer day than the build. The first automatic request failing is not the visitor's mistake, so it shows no error (the banner says why and the build-time answer stays); a request the visitor starts does. The table lists the newest day first and scrolls inside its own box with a held header; the chart sits beside it from 64rem; code samples are folded; the fixed presets (22 May 2022 cut, all of 2021) are replaced by three relative ones. On a short screen (`max-height: 36rem`) the box and the held header go away and the page scrolls, because a 320 px scroll box in a 390 px landscape phone traps touch scrolling (this is what the `fixed-bar-budget` probe flagged: 31.5% of the viewport, now 0).
- **Written from memory, not retrieved.** The range switch, city select, banner, folded samples and playground layout: no registry (shadcn, React Bits, Magic UI, Aceternity) ships them for a plain-CSS, prerendered page, the same reason as the chart and table above. The `design-source` scan of `index.css` found no Tier B defect.
- **Status page copy fixed.** It said the site is redeployed with each data commit and the API reads its files at start-up; both were true before the run-time refresh and are not now. README and `docs/GO-LIVE.md` say the same, and the README has a Settings table (`DATA_REMOTE`, `DATA_BASE_URL`, `DATA_TTL_SECONDS`, `PORT`, `SITE_URL`).
- **An error boundary around the page body.** The audit found that one bad value from the API could blank the whole site. A render error now shows a message, a link to the docs and a Reload button; the header, banner and footer stay.
- **How it was tested.** Pure rules (windows, chunks, states, shape checks, sentences, example paths) have node tests. The pages and components are drawn on the server through Vite's `ssrLoadModule` with made-up live states: fresh, two days behind, five days behind, offline, a day newer than the build, an API without `last_change`, empty, one-row, flat and 3,417-day ranges, a failed chart, loading, a result over 100 rows and one over four series. Three deliberate mutations (stale limit 2 to 3, a May 2022 preset typed back in, an off-by-one window) each failed a test. A headless Chrome run against the real app checked 51 behaviours, including a server whose data was cut at 19 Oct (stale), a server with a day newer than the build, and the API blocked.

### Audit of `backend/src/data-store.js` (`prod-bug-auditor`, one pass, verdict warn, no failing dimension)

Each finding was re-read against the code before acting.

- **Fixed: `changes.json` was never tied to `daily.json`.** A stale `changes.json` next to a new `daily.json` passed, and the ETag shortcut then kept it. `validateDataset` now derives the expected changes from the days and refuses a missing, invented, duplicated or out-of-order change (a change dated on the first stored day, which has no day before it, must end at that day's price). A refused dataset stores no ETag, so the next check fetches the full set (tested).
- **Fixed: a dataset from the future locked out every real one** (the "never go backwards" rule became a ratchet, and `days_behind` clamps at 0 so the status page said "Current"). The newest day may now be at most two days ahead of today in India.
- **Fixed: truncation.** A dataset that starts later or has fewer days than the one in memory is refused.
- **Fixed: meta was served verbatim.** `validateDataset` now returns meta reduced to nine checked fields (https `source_url`, text `sha256`, bounded strings, real dates), refuses the rest, and error text repeats at most 40 printable characters of any value from the file. The frontend checks the same fields before it draws them, so a `javascript:` link or a missing `sha256` cannot reach `/status`.
- **Fixed: the size cap ran after the body was buffered.** The body is now read as a stream and dropped at the cap (`maxBytes`, 8 MB, the same limit).
- **Fixed: `daily.json` and `changes.json` are fetched together**, so a cold start costs two round trips, not three. **Fixed: failed refreshes are logged** (one line per attempt, spaced by the backoff); the tests keep the store silent.
- **Not done, on purpose.** (1) Comparing overlapping days with the loaded ones to catch an edited historical price: the API cannot tell an edit from a restatement the owner approved in `ingest/approved-restatements.json`, and refusing every difference would freeze the API on old data after a legitimate restatement. The boundary is write access to the repository's `main` plus the ingest `diff-history` guard; revisit with a signed manifest if that boundary weakens. (2) `waitUntil` for a refresh still running when Vercel freezes the instance: it needs `@vercel/functions`, and the cost is one spurious timeout line and a 60-second backoff on thaw. (3) Per-file hashes in meta: not needed now that changes are derived from days and days are tied to meta by first date, last date and count. (4) The kill switch `DATA_REMOTE=off` needs a redeploy to take effect.

## 2026-10-24 — Price board shows the change over 1, 7 and 30 days, not the last change (owner request after go-live)

- **Why.** The board printed "Last change +2.61 on 25 May 2026" under all eight prices. It was true (PPAC's table has no revision after 25 May 2026) but eight identical lines carrying a five-month-old date read as a hardcoded May result, which the owner had asked to remove. The owner asked for the latest prices and, if anything more, the last day, week and month.
- **Now.** Today's price, and under it the change over the last 1, 7 and 30 days: the newest price minus the price that many days earlier, rounded to paise, `0.00` when it did not move, `–` when that day is not in the data (`lib/recent.js`). No date of an old revision appears anywhere in the board.
- **Data.** After meta and the newest day, the live load asks `/v1/prices?from=<newest minus 30 days>&to=<newest>` (31 rows, every city). If that one call fails the state is still live and the board shows today's prices alone, with no made-up zeros. First paint and offline use `examples.board`, captured at build time. `meta.last_change` stays in `/v1/prices/latest` for API users, but no page reads it, and `last_moves` is gone from the snapshot.
- **Left in place on purpose.** The list "Largest single-day moves in Delhi since 16 Jun 2017" (history; it includes 15 May 2026) and the docs "Price changes" example (the real changes of the last year, all in May 2026 because nothing has moved since). Both are labelled, and both are one change away from removal if they still confuse.
- **Tested.** Unit tests for the change maths (rounding, negative, missing day, missing city, no rows); state tests for the extra request (counted from the newest day, survives its failure, does not swallow an abort); render tests that every board, prerendered, live or stale, has eight blocks of 1, 7 and 30 days and none of "Last change", "May" or a raw date; a day newer than the build shows +1.38 on Delhi petrol for all three periods. Headless Chrome on the real app at 1280, 390 and 320 px: no overflow, no page error; `mobile-check` on `/`: 0 fail.

## 2026-10-25 — A price that has held for a month says how long, instead of rows of 0.00 (owner feedback after the deploy of `16d7833`)

- **Why.** The deployed 1, 7 and 30 day board showed `0.00` in all 24 cells, because PPAC's table has no revision after 25 May 2026 and all eight prices have been flat since. The numbers were true and told a visitor nothing; the owner asked what the page is for if everything reads zero.
- **Now.** Under a price whose last change is 30 days or more before the newest day (`HOLD_NOTICE_DAYS`, the longest of the three periods) the board prints "Unchanged for N days" and "since <date of the change>". N counts from that date to the newest day, so it grows by itself every day and does not read as a fixed May result (the earlier complaint was the same date repeated with no count). A price that moved in the last 30 days still shows its 1, 7 and 30 day change, and the caption says which of the two the visitor is looking at.
- **Data.** No new request. `meta.last_change` was already in the `/v1/prices/latest` answer (it is what the old "Last change" line read). `lib/live-state.js` now keeps its dates as `lastChange`, each entry checked as a real date or dropped; the build's copy comes from the stored latest example.
